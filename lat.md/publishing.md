# Publishing

How the plugin reaches users and how the website is built; both are automated from tags and pushes to `main`.

## Plugin releases

A pushed tag equal to the manifest version (no `v`) triggers `.github/workflows/release.yml`, which tests, builds and attaches `main.js`, `manifest.json` and `styles.css`.

The workflow also attests build provenance for `main.js` and `styles.css`, which the community review asks for.

The review flags dynamic code in `main.js`, so the plugin's esbuild config rewrites the `Function('return this')()` fallback that cytoscape inlines from lodash to `globalThis`; the Cypher evaluator's method is `evaluate`, not `eval`. The review lints the whole repository, so Node built-in imports and bare `setTimeout` in `node-vault` and `vscode` (never bundled into the plugin) show up as warnings. Those warnings do not apply to the plugin. Rendered Quarto output under `articles/` is gitignored and must stay untracked, or its Bootstrap CSS floods the review's CSS lint. The demo vault zip on the release is reported as an extra file that Obsidian ignores.

Obsidian's installer reads `manifest.json` from `main` and downloads the assets of the release tagged with that version, so a version bump on `main` without its release makes every install fail with "Failed to install plugin". Push the release commit and its tag together (`git push --atomic origin main <version>`). `scripts/check-plugin-install.mjs` (`npm run check:install`) repeats the installer's downloads; it runs as the last release step and in `.github/workflows/install-check.yml` every six hours and after CI on `main`. Specs are in [[tests/plugin-install]].

Each release adds a section to the root `CHANGELOG.md` (plugin, CLI, core and sidecar) in the release commit; the VS Code extension keeps `packages/vscode/CHANGELOG.md`. The release workflow uses that section as the GitHub release body, extracted by `scripts/release-notes.mjs`, and appends GitHub's generated pull request list; a tag without a section still gets its release, with a warning, because a tag without a release breaks every Obsidian install.

The plugin is listed as **Typed Graph** (id `typed-graph`): directory rules forbid names with `Obsidian` or variations like `Obsi-`, so the earlier name Obsigraph was rejected; the repository is `Volland/typedgraph` and the site is https://typedgraph.org (GitHub does not redirect the old `volland.github.io/obsigraph/` Pages URLs after a rename), while the npm scope `@obsigraph/*`, CSS classes and `OBSIGRAPH_*` variables keep the old name internally. Obsidian reads `manifest.json` and `versions.json` at the repository root, so `scripts/version-bump.mjs` keeps the root manifest, `packages/plugin/manifest.json`, `versions.json` and every package version in step, then refreshes `package-lock.json`; workspaces depend on `@obsigraph/core` as `*` so a bump never sends `npm ci` to the registry for an unpublished version. Store listing is a web submission at community.obsidian.md (Obsidian account plus linked GitHub), followed by an automated review; it passed and the plugin is listed at https://community.obsidian.md/plugins/typed-graph (install link `obsidian://show-plugin?id=typed-graph`); `obsidianmd/obsidian-releases` only mirrors the directory, so pull requests to its JSON no longer list a plugin.

## Website

`site/` is a static site (home, docs, live demo) published to GitHub Pages by `.github/workflows/pages.yml` at https://typedgraph.org/.

The demo bundles the real core engine, schema styling and the plugin's pure rendering modules (`site/src/demo.ts`, built by `npm run site:build`) over an editable sample vault, with a seeded force layout so screenshots are stable. Screenshots in `site/assets/screenshots/` are taken from the demo with headless Chrome (`?example=N&theme=light|dark`). The logo, a crystal of graph facets with a ladybug, is `site/assets/logo.svg`.

`site/build-spec.mjs` also renders the [[shacl#Typed Graph Schema]] specification, current version 0.3, to `spec/tgs/v0.3/` (with every archived version such as 0.1 and 0.2 from `spec/tgs/archive/` to its own `spec/tgs/v<version>/`, and `spec/tgs/` redirecting to the latest) and the `tgs:` namespace page to `ns/tgs/`, copied into the Pages artifact. Besides home, docs and demo, the site has `example.html` (the [[publishing#Example vault]] with a download link) and a blog: `blog.html` indexes long-form articles kept as flat pages (`blog-typed-graph.html` on the plugin's features, `blog-sidecar-rag.html` on the sidecar, vectors, GraphRAG and MCP, `blog-tg-cli.html` on the tg CLI for developers `blog-tg-vs-lat-md.html`, an honest comparison with lat.md that must be rechecked against its current version before changes, `blog-why-typed-graph-for-code.html`, an essay on typed links and why intent is written by hand, `blog-typed-graph-schema.html`, on schema notes, edge types and the SHACL exchange, whose output sizes come from a real export of the example vault, and `blog-okf-ready.html`, a guide to making a vault conformant with [[okf|Open Knowledge Format]] whose report and query numbers come from real runs over the demo vault and Google's GA4 sample bundle), because the Pages workflow publishes `site/*.html`. Two of them, `blog-typed-graph-for-coders.html` (a deep dive on typed graphs for developers) and `blog-code-ontology.html` (using the [[cli#Code ontology]] by role), are rendered from `articles/*.md` by `site/build-articles.mjs` (`npm run site:articles`); edit the Markdown and rerun it, and its `@tg:` examples are written with an empty span so `tg check` does not read them as annotations. The home page leads with Typed Graph as a shared space for agents and humans, an install strip (Claude Code, VS Code and forks, Obsidian) and a developers section for `tg`, and `docs.html` has a CLI reference. Audience pages `agents.html`, `obsidian.html`, `teams.html` and `install.html`, plus `compare.html` (Typed Graph beside lat.md, plain Obsidian and vector-only memory; its lat.md facts must match `blog-tg-vs-lat-md.html`), are hand-written with the same header and footer as the other pages, and the first three sit in the top navigation. Short looping clips in `site/assets/demos/` (muted `<video>` with WebM and MP4 sources and a poster, no third-party player; `site.js` stops autoplay under reduced motion) show a Zettelkasten in the live demo on the home and Obsidian pages and real `tg` output on an example project on the home, Teams and Agents pages; `scripts/record-demos/` regenerates them with Playwright. Two launch articles, `blog-shared-space.html` (manifesto) and `blog-claude-code-memory.html` (a tutorial whose commands were run against the built CLI), are rendered from `articles/*.md`. `blog-specs-that-know-their-code.html`, also rendered from `articles/*.md`, tells how this repository's OpenSpec requirements were traced to code, tests and docs with [[cli#Requirement trace]]; its `tg trace`, `tg check` and `tg cypher` output and audit counts come from real runs, so rerun them before editing the numbers. `blog-spec-frameworks.html`, rendered from `articles/bring-your-own-spec-framework.md`, introduces [[cli#Spec frameworks]]; its `tg init`, `tg trace`, `tg check` and `tg cypher` output comes from a real run of the built CLI on a new project where `tg init --spec speckit,adr --install-spec` installed Spec Kit, so rerun it before changing the numbers. The hand-written `spec-frameworks.html` lists the supported frameworks, their ids and installers, and how to add one: typed lat.md sections, mapping onto a supported format, or a reader contributed to `packages/core`; the home page's *Bring your spec framework* section (`#spec-frameworks`) is a tab picker (`[data-spec]` buttons handled in `site.js`) showing each framework's `tg init --spec` command and ids, and links there. Both `index.html` and `docs.html` have a VS Code install section (`#install-vscode`) for the [[vscode]] extension, linking to the VS Code Marketplace and Open VSX. The brand in titles, headers, footers and prose is Typed Graph, matching the Obsidian directory name; only the VS Code extension's display name and command titles are still TypeGraph, so install hints say to search for *TypeGraph* there. Numbers and sample responses in the RAG article come from a real sidecar run over the example vault with local `nomic-embed-text`. 

German legal pages (`impressum.html`, `datenschutz.html`, `agb.html`, in German, `noindex`) are linked from every footer. The privacy policy relies on the site loading nothing from third parties, setting no cookies and storing only the theme choice in `localStorage`; adding analytics, fonts or embeds from another origin requires updating it.

## Example vault

`example/` is a demo vault (a small research lab) that uses every plugin feature and carries the user manual: concepts, a Cypher course, a query gallery, sidecar usage and a diagnostics playground.

Every `graph-query` block, embed, schema warning and stub in it is checked by `packages/plugin/test/example-vault.test.ts` (specs in [[tests/example-vault]]), so the manual fails the build when it drifts from the engine. Examples that need the sidecar are written in plain fences. `npm run example:install` (`scripts/install-example.mjs`) builds the plugin into `example/.obsidian/plugins/typed-graph/`, which is gitignored; only `community-plugins.json` is committed. Each release also attaches `typed-graph-demo-vault.zip`: the vault with the freshly built plugin preinstalled, linked from the website and README as `releases/latest/download/typed-graph-demo-vault.zip`.

## Ontology gallery

`ontologies/` holds ready-made Typed Graph ontologies as plain Markdown vaults, offered for download on `site/ontologies.html`.

Each folder has `Types/` (schema notes in [[shacl#Typed Graph Schema]]), `Examples/` and a README: `zettelkasten` (the method's five note types, book, article and paper sources with writers (papers can also `cites` each other), highlights and topics; writers and books are `Writer` and `BookSource` so it composes with the library's `Author` and `Book`), `library`, `requirements`, `agents` and `okf` (a data catalog that exports as an Open Knowledge Format bundle, see [[okf]]), plus `core` for edge types several share, declared once so the ontologies can be combined (see [[tests/ontology-gallery]]). `scripts/build-ontologies.mjs` (`npm run site:ontologies`, run by the Pages workflow, needs `zip`) writes `site/ontologies/<id>.zip` with the shared `Core.md` added, `all.zip` with every ontology composed, and the schema notes as single files; the output is gitignored. `packages/core/test/ontologies.test.ts` checks every ontology and their composition. `site/src/ontology-map.ts` (bundled with the demo by `site/build.mjs` into the gitignored `assets/ontology-map.js`, with the ontology notes read at build time) draws, with the plugin's own styler and renderer, a tabbed schema map of each ontology and a seven-step walkthrough of the Zettelkasten examples whose steps are in `site/src/trail-steps.ts`; the walkthrough pauses autoplay under reduced motion. The article `blog-composable-ontologies.html` is rendered from `articles/composable-ontologies.md` like the other long articles. The long read `blog-zettelkasten-thinking-machine.html` (from `articles/zettelkasten-thinking-machine.md`) builds the Zettelkasten, composes it with the library through two-label notes, and runs a dozen queries; its validator output and query results come from a real run over the two ontologies' examples plus the bridge notes shown in the article.
